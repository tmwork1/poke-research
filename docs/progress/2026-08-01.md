# 2026-08-01

## Discord運用アラートで断続的な `/items` `/papers` 500エラーを検知（対応済み）

07/31〜08/01の2日間でDiscordの運用アラート（`sendOperationalAlert`）が計6回発火。内訳は `/items`/`/papers` に対して `{"message":"error code: 523\n"}`（Cloudflare: Origin Is Unreachable）、`{"message":"error code: 1016\n"}`（Cloudflare: Origin DNS Error）、`{"message":"Internal server error."}`（Supabase側の汎用500と見られる、文言が自前の`jsonError('Internal Server Error', 500)`と一致しない）が散発。

### 調査

- `SUPABASE_URL`（`*.supabase.co`）はSupabase自身がCloudflareを前段に置いているため、Workerからのfetchが失敗する523/1016は、Cloudflareエッジ〜Supabaseオリジン間の一過性の接続断を示す。単発ではその都度自然復旧しており（発生直後に本番URLへアクセスすると200 OK）、アプリ側のコードバグではない。
- 直近のデプロイ（07/25 05:28、PR #84）から6日経っており、コード変更が引き金とは考えにくい。
- `/items`・`/papers` はページ表示時に `Promise.all` でSupabaseへ3〜4本の並列リクエスト（`fetchCatalogItemsPage`/`fetchTopTags`/`fetchCatalogSources`/`fetchBookmarkedItemIds`）を投げる設計のため、どれか1本が一過性エラーに当たると全体が失敗し、他ページより統計的にアラートが出やすい。
- Supabaseステータスページには07/31にDNS遅延・Management API性能劣化のインシデントが記録されていたが、エラー発生時刻と完全には一致せず、ステータスページに載らない短時間のエッジ瞬断も混ざっていると見られる。

### 対応

参照系（GET/HEAD）は冪等なため、Supabaseクライアントのfetch層に1回だけの自動リトライを追加（`src/lib/resilient-fetch.ts`の`withTransientRetry`、`src/lib/supabase.ts`で`countingFetch`の外側に重ねて`getSupabaseClient`/`getSupabaseAdminClient`両方に適用）。5xx〜530（Cloudflareのオリジン接続エラー521〜527, 530を含む範囲）またはfetch自体の例外を検知した場合のみ、300ms待って1回だけ再試行する。書き込み系（POST/PATCH/DELETE）は冪等性を保証できないためリトライ対象外。

`tests/resilient-fetch.test.ts`でGET成功時は再試行しないこと、523/例外時は1回だけ再試行して復旧すること、再試行しても失敗する場合は最後のレスポンスをそのまま返すこと、4xxや書き込み系はリトライしないことを検証。`npm test`（144件）・`npm run build`とも成功。

### 教訓

- CloudflareにホストされたWorkerからCloudflareを前段に持つSupabaseへ接続する構成は、両者のエッジ間の瞬断がそのままユーザー向け500として表面化しやすい。参照系だけでも1回リトライを入れておくと、この種の外部要因による瞬断をアプリ層で吸収できる。
- 1回のアラートだけでは「Supabase側の一時的な問題」と判断して対応不要としていたが、複数日にまたがる再発パターンを見て初めてリトライという恒久対応が必要だと判断した。単発のアラートで済ませず、一定期間分のログを横断して頻度を確認することが重要。
