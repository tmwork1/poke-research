# 2026-09-19

## 週次DBレビューのDiscordレポートが毎週同じ内容になっていた件

### 発端

Discordへ毎週月曜に届く「週次DBレビュー」の内容が毎回同じ、という指摘。

### 原因（バグ）

`src/lib/maintenance-review.ts` の `detectDuplicateItemCandidates()` / `detectDuplicateSourceCandidates()` が `.range()` を使わずに `select()` しており、Supabase（PostgREST）の既定行数上限1000件で打ち切られていた。本番の `items` は1219行あったため、毎週 id 昇順の先頭1000件だけを突き合わせていたことになり、新着記事がどれだけ増えても検出結果（と先頭5件の例示）が変化しなかった。同じ欠陥が `scripts/db/detect-duplicate-items.mjs` / `detect-duplicate-sources.mjs` にもあった。

修正は1000件ずつ `.range(offset, offset + pageSize - 1)` でページングして全行を取得する形（PR #90、修正自体は codex に実施させ、本セッションで検証）。修正後に本番DBへ読み取り専用スクリプトを実行し、従来は届かなかった id 1000超の重複候補が検出されることを確認（items 36組・sources 1組）。

### 繰り返し作業が出ないようにするための対応

検出できるようになっただけでは、統合されない候補が毎週再掲され、同じ判断を毎週やり直すことになる。3段構えで対応した。

1. **既存の重複を解消**: items 36組を1組ずつ内容確認し、31件を `merge-item.mjs` で統合（同一著者のQiita↔Zennクロスポスト4件、arXiv版↔学術誌版・preprint↔OpenAlex ID行など4件、Zenodoのconcept/version DOIペア23件）。sources は「はてなブログ」の `hatenablog.com` / `hatenablog.jp` を統合（#157→#57、items 15件を付け替え）。
2. **「重複ではない」判断の記録**: `duplicate_review_dismissals`（migrations/030）に人手の判断を記録し、週次レビューと `detect-duplicate-*.mjs` の出力から除外する。登録は `scripts/db/dismiss-duplicate.mjs`。通知には「除外済み N 組を除く」を必ず併記し、候補0組が「本当に無い」のか「除外で消えている」のかを通知だけで区別できるようにした。今回登録したのは2組（別著者の同名記事「ポケモンで学ぶ統計学」、原論文 PokéLLMon とその日本語訳解説記事）。
3. **重複の発生源を止める**: 36組の大半は、OpenAlex が同じ成果物を別Workとして返すこと（Zenodoの concept DOI と version DOI、OSFのpreprintとOpenAlex ID行）が原因で、統合しても毎週新たに増え続ける構造だった。`external_url` の UNIQUE 制約では防げないため、`items.normalized_title`（migrations/031、記号・空白を除去して小文字化した生成列）を追加し、OpenAlexインポーターが収集時に「同じ正規化タイトルの論文が既にある／同一バッチ内で既に採用済み」なら AIレビュー・DB書き込みを行わずスキップするようにした（`findExistingNormalizedTitles`、`findDuplicateTitleUrls`）。同名の別論文を取りこぼす可能性はあるが、重複が増え続ける実害の方が大きいと判断した（取りこぼしは skipped 理由でログに残る）。

JS側の正規化（`src/lib/importers/title-dedup.ts` の `normalizeTitleForDedup`）と生成列の定義がずれると重複判定が無言で効かなくなるため、本番1188件で突き合わせて一致を確認した。初版では JS の `\p{N}` が囲み数字（①②、Unicodeカテゴリ No）を残す一方 PostgreSQL の `[:alnum:]` は除去するため14件が不一致になっており、`\p{Nd}` に変更して0件にした。

### 結果

`detect-duplicate-items.mjs` / `detect-duplicate-sources.mjs` とも候補0組（items は「除外済み 2 組を除く」）。`npm test`（149件）・`npx tsc --noEmit`・`npm run build` すべて成功。migrations 030・031 は本番Supabaseへ適用済み。

### 教訓

- PostgRESTの既定上限（1000行）は、テーブルがその行数を超えた時点から「エラーにならずに静かに結果が変わらなくなる」形で表面化する。全件走査を前提とするバッチ（重複検出のような総当たり）では、`.range()` によるページングを最初から入れておく必要がある。
- 「毎週同じ通知が届く」は、通知の内容が変わらない＝異常、と気づけるシグナルでもあった。0件の場合でも件数の内訳（除外済みN組）を添えておくと、沈黙と正常の区別がつく。
