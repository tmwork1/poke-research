# 2026-09-19

## 週次DBレビューのDiscordレポートが毎週同じ内容になっていた件

### 発端

Discordへ毎週月曜に届く「週次DBレビュー」の内容が毎回同じ、という指摘。

### 原因（バグ）

`src/lib/maintenance-review.ts` の `detectDuplicateItemCandidates()` / `detectDuplicateSourceCandidates()` が `.range()` を使わずに `select()` しており、Supabase（PostgREST）の既定行数上限1000件で打ち切られていた。本番の `items` は1219行あったため、毎週 id 昇順の先頭1000件だけを突き合わせていたことになり、新着記事がどれだけ増えても検出結果（と先頭5件の例示）が変化しなかった。同じ欠陥が `scripts/db/detect-duplicate-items.mjs` / `detect-duplicate-sources.mjs` にもあった。

修正は1000件ずつ `.range(offset, offset + pageSize - 1)` でページングして全行を取得する形（PR #90、修正自体は codex に実施させ、本セッションで検証）。修正後に本番DBへ読み取り専用スクリプトを実行し、従来は届かなかった id 1000超の重複候補が検出されることを確認（items 36組・sources 1組）。

### 繰り返し作業が出ないようにするための対応

検出できるようになっただけでは、統合されない候補が毎週再掲され、同じ判断を毎週やり直すことになる。3段構えで対応した。

1. **既存の重複を解消**: items 36組を1組ずつ内容確認し、31件を `merge-item.mjs` で統合（同一著者のQiita↔Zennクロスポスト4件、arXiv版↔学術誌版・preprint↔OpenAlex ID行など4件、Zenodoのconcept/version DOIペア23件）。sources は「はてなブログ」の `hatenablog.com` / `hatenablog.jp` を統合（#157→#57、items 15件を付け替え）。
2. **「重複ではない」判断の記録**: `duplicate_review_dismissals`（migrations/030）に人手の判断を記録し、週次レビューと `detect-duplicate-*.mjs` の出力から除外する。登録は `scripts/db/dismiss-duplicate.mjs`。通知には「除外済み N 組を除く」を必ず併記し、候補0組が「本当に無い」のか「除外で消えている」のかを通知だけで区別できるようにした。今回登録したのは2組（別著者の同名記事「ポケモンで学ぶ統計学」、原論文 PokéLLMon とその日本語訳解説記事）。
3. **重複の発生源を止める**: 36組の大半は、OpenAlex が同じ成果物を別Workとして返すこと（Zenodoの concept DOI と version DOI、OSFのpreprintとOpenAlex ID行）が原因で、統合しても毎週新たに増え続ける構造だった。`external_url` の UNIQUE 制約では防げないため、`items.normalized_title`（migrations/031、記号・空白を除去して小文字化した生成列）を追加し、OpenAlexインポーターが収集時に「同じ正規化タイトルの論文が既にある／同一バッチ内で既に採用済み」なら AIレビュー・DB書き込みを行わずスキップするようにした（`findExistingNormalizedTitles`、`findDuplicateTitleUrls`）。同名の別論文を取りこぼす可能性はあるが、重複が増え続ける実害の方が大きいと判断した（取りこぼしは skipped 理由でログに残る）。

JS側の正規化（`src/lib/importers/title-dedup.ts` の `normalizeTitleForDedup`）と生成列の定義がずれると重複判定が無言で効かなくなるため、本番1188件で突き合わせて一致を確認した。初版では JS の `\p{N}` が囲み数字（①②、Unicodeカテゴリ No）を残す一方 PostgreSQL の `[:alnum:]` は除去するため14件が不一致になっており、`\p{Nd}` に変更して0件にした。

### 結果

`detect-duplicate-items.mjs` / `detect-duplicate-sources.mjs` とも候補0組（items は「除外済み 2 組を除く」）。`npm test`（149件）・`npm run build` すべて成功。migrations 030・031 は本番Supabaseへ適用済み。

### 作業中に判明した注意点

作業開始時のローカル `main` が origin より3PR分（#87 cronのGitHub Actions移設、#88・#89 週次レビューのCPU上限超過対策）古く、その古い `main` から作業ブランチを切っていた。途中で気づき `origin/main` へ rebase して解消したが、そのまま進めていれば #87〜#89 の変更を巻き戻す形の PR になっていた。1000行上限のバグ自体は `origin/main` にも残っていたため、原因の結論と修正内容は変わらない。作業前に `git fetch` で origin との差分を確認する。

### 教訓

- PostgRESTの既定上限（1000行）は、テーブルがその行数を超えた時点から「エラーにならずに静かに結果が変わらなくなる」形で表面化する。全件走査を前提とするバッチ（重複検出のような総当たり）では、`.range()` によるページングを最初から入れておく必要がある。
- 「毎週同じ通知が届く」は、通知の内容が変わらない＝異常、と気づけるシグナルでもあった。0件の場合でも件数の内訳（除外済みN組）を添えておくと、沈黙と正常の区別がつく。

## 記事収集の検証と、article/paper が全件棄却されていた件の修正

### 発端

「最近の記事収集は問題なくできているか」の検証依頼。

### 検証結果

収集ジョブ（GitHub Actions の日次cron）自体は正常で、直近14日の失敗は arXiv の 429 が2件（9/12・9/13）のみ。fetched も各プロバイダで出ている。一方で**新規記事の採用が2026-07-26以降ほぼゼロ**だった。

| route | 直近60日の新規 | うち採用 |
|---|---|---|
| hatena | 219 | 1 |
| openalex | 60 | 0 |
| qiita | 18 | 0 |
| feed | 11 | 0 |
| zenn | 5 | 0 |
| arxiv | 3 | 0 |

（github の300件/220採用は 2026-07-22 の手動Claudeレビュー分で cron 由来ではない。）旧プロンプト期の採用率は6割前後だったため、明確な断絶。

### 原因

`OPENAI_REASONING_EFFORT` の既定値 `minimal` が、STEP1〜5（article）・STEP1〜3（paper）に精緻化された現行プロンプトに対して力不足で、多段判定が完了せずに全件 `accepted=false` になっていた。棄却理由は内容評価ではなく「STEP1の言語判定が未完了」「本文が提供されていない」（実際には本文4000字を渡している）といった判定の中断で、reason には「主題内と判断」と書きながら `accepted=false` を返す自己矛盾も複数あった。

これは 2026-07-23 に `kind='repo'` について特定済みの現象と同一（d688f7f で repo のみ下限を `low` に引き上げ済み）で、article/paper は minimal のまま残っていた。プロンプトが精緻化された7月中旬以降に顕在化したとみられる。

**副次的な実害**: `minimal` では `summary` が空で返るケースがあり（28件中3件）、これは本番の `parseAiResponse` が例外を投げる条件＝記事が棄却としても記録されずDBから消える経路にあたる。表面化していた棄却約470件は下限値で、記録なく失われた記事が別にある。

### モデルグレードの検証

「`gpt-5-nano` というグレードが必要十分か」を、本番データ28件（適合12・不適合12・境界4、人手ラベル付け）の読み取り専用スクリプトで5構成を総当たり比較した（詳細は [docs/optimization/filter-accuracy.md](../optimization/filter-accuracy.md)）。

| 構成 | 正解 | 見逃し | 誤採用 | JSON不備 | 出力tok（28件） |
|---|---|---|---|---|---|
| nano / minimal（修正前の本番） | 12/24 | 12/12 全滅 | 0 | 3 | 6,562 |
| nano / low | 23/24 | 1 | 0 | 0 | 20,304 |
| nano / medium | 23/24 | 1 | 0 | 0 | 77,771 |
| mini / minimal | 22/24 | 1 | 1 | 0 | 6,416 |
| mini / low | 23/24 | 0 | 1 | 0 | 13,947 |

nano/low の唯一の見逃し（361「スイッチを自動化してポケモンの乱数消費させたい」）は「STEP4: チートツールの作成・配布」による棄却で、bf84ece で明示BANした基準の適用としては正しい。medium は low と完全同結果で出力トークンのみ3.8倍。mini は見逃しこそ減るが「ポケモンを題材にしているが実データ・仕様を扱わない記事」（Unityホログラム記事）を conf 0.86 で採用する方向にブレる。**モデルのグレードではなく推論コストが効く**という、実験2・6（`gpt-5.4-nano`）と同じ結論が再現した。

### 対応

`src/lib/importers/article-ai.ts` の `MIN_REASONING_EFFORT_BY_KIND` に `article`/`paper` を追加し、下限を `low` に引き上げた（実装は codex に委譲）。`kind` 未指定も `buildSystemPrompt` と同じく article 扱いで `low` になる。`OPENAI_REASONING_EFFORT` に `medium` 等が明示設定されていればそれを尊重する既存の挙動は不変で、`src/lib/openai.ts` の既定値（`minimal`、タグ解説など他用途が使う）も変更していない。プロンプト文言は無変更。`tests/article-ai.test.ts` に kind × 設定値の20ケースの回帰テストを追加。

### 検証

`npm test`（169件）・`npm run build` ともに成功。

### 残課題

- 2026-07-26 以降に棄却された約470件の再判定（OpenAI課金・本番DB書き込みを伴うため、実施可否は別途相談）。
- `import_runs.inserted` は採用分しか数えないため、棄却行が毎日入っていても 0 と表示される。週次レビューの「直近7日 import_runs 無し」警告も発火しないため、この2か月の異常は通知では検知できなかった。採用0件が続く状態を検知する仕組みの追加を検討する。
- リポジトリ直下の `env` / `env.production` / `dev.vars`（本来はドット付きファイル）が `.gitignore` の対象外で未追跡のまま残っている。APIキーを含むため誤コミット防止の対処が必要。
